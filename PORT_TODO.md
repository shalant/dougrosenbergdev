## SEO / GEO / traffic impact of this refactor (2026-09-08)

Net assessment: **structurally positive, if the eventual deploy is done carefully** - the port fixes exactly the crawlability gap the live site's own `blazor-wasm-geo-audit` blog post identified, while preserving everything that matters for ranking continuity.

**Why it should help:**
- The live site is a client-rendered Blazor WASM SPA - nothing real exists until ~3-4MB of WASM downloads and boots, which is why it needed a hand-maintained "static pre-paint" hack for the homepage plus a separate Playwright prerendering pipeline (`tools/prerender/`) just so crawlers see real content at all. This site needs none of that: every page is complete, real HTML at build time, for every crawler, on a plain GET - the exact thing that blog post audited as broken.
- Structured data (`Person`/`WebSite`/`SoftwareApplication` globally, `Services`/`FAQPage`/`BlogPosting` per-page) is baked directly into static HTML instead of depending on the prerender pass catching it correctly.
- Lighthouse's SEO category scores a clean 1.0 locally.

**Continuity preserved (the things that would otherwise reset rankings/history):**
- Same domain and identical URL structure for every route - Google recrawls URLs it already has indexed rather than needing to discover anything new.
- Same GA4 property ID (`G-3H1NB9ES0L`) carried over - no analytics history split.
- Canonical URLs, OG/Twitter meta, and `sitemap.xml` (now auto-generated by `@astrojs/sitemap` from actual routes instead of hand-maintained) all point at the same real domain throughout.

**One intentional content change worth remembering:** the homepage hero's visible subtitle changed from "software engineer building custom web apps..." to a sentence about the current ERP project - "software engineer" is now less prominent in the hero's actual on-page text (still present in the `Person` schema and `<title>`). Small, real keyword-emphasis shift, and it happens to point the same direction as the recruiter-visibility constraint above.

Result: **0.84** - accessibility/best-practices/SEO all still a clean 1.0. So the "local lab conditions" theory in the old version of this note was only half right: real HTTP/2 + compression from the edge helps, but doesn't close the gap to 0.9 on its own, because the remaining gap isn't a network artifact - it's Lighthouse's standard mobile-throttling simulation (`formFactor: mobile`, 4x CPU slowdown, ~1.6 Mbps) plus LCP scoring **0.42** specifically: the LCP element is the hero `<h1>` text (not an image), and 84% of its 4.3s LCP is "Render Delay," not TTFB/load time - consistent with the classic `font-display: swap` behavior where Chrome's LCP timestamp tracks the *font-swap repaint*, not the initial fallback-font paint, so a slow-under-throttling custom-font fetch (even preloaded) pushes the reported LCP later even though real users never see invisible text. Every other metric is fine (FCP 1.6s/0.93, TBT 50ms/1.0, CLS 0/1.0, Speed Index 3.0s/0.94) - this is narrowly an LCP-attribution issue, not a general slowness problem. `categories:performance` stays at `warn` (not `error`) in `lighthouserc.json`.
