## GA4 Consent Mode (2026-09-28)

The same SEO/GEO audit also reviewed GA4's setup and found it firing unconditionally with no consent handling — a real gap if the site ever gets EU/UK traffic that needs GDPR-compliant opt-in. Implemented Google Consent Mode v2:

- `BaseLayout.astro`'s head script now calls `gtag('consent', 'default', {...})` — all four signals denied by default — before the existing `gtag('js', ...)`/`gtag('config', ...)` calls, so nothing is collected ahead of a real choice. `ad_storage`/`ad_user_data`/`ad_personalization` stay denied permanently since this site runs no ads/remarketing; only `analytics_storage` is ever toggled.
- New `src/components/ConsentBanner.astro` (mounted from `BaseLayout.astro` directly, not `Header.astro`, so it renders on every page including `404.astro`) — a bottom bar with Accept/Decline, styled with existing tokens only (no new hexes/type family), deliberately not using a filled `--teal` button so it doesn't spend the page's one-bold-accent budget on a compliance banner.
- New `public/js/consent.js` (`DrConsent`, same delegated-init pattern as `DrNav`/`DrTheme`/`DrContactDialog`) shows the banner only when `localStorage['dr-consent']` is unset, and calls `gtag('consent', 'update', {analytics_storage: ...})` on Accept/Decline. A returning visitor's stored choice is read synchronously in the head script itself, so the correct consent state is set before GA4's config call even fires — the banner never flashes for them.
- Verified manually (`npx playwright`'s pinned Chromium via `executablePath`, since this repo's `@playwright/test` version doesn't match the sandbox's pre-installed browser revision — a pre-existing environment mismatch, not caused by this change): first-visit banner shows with `analytics_storage: denied` by default; Accept grants it and persists; Decline keeps it denied and persists; a returning "granted" visitor gets the right default with no banner flash; the header contact dialog still opens fine with the banner present (no z-index/click-interception conflict). `npm run build` and `check-links.mjs` both clean (794 refs, only the pre-existing unrelated `/archive/dist/portfolio` gap).

### Region-scoped consent default (2026-09-28 correction)

The global default-deny above turned out to have a real cost, caught while debugging the key-event issue: with `analytics_storage` denied for every visitor until they click Accept on a brand-new banner, GA4 can't set the persistent `_ga` client-ID cookie for almost anyone, so nearly every pageview looks like a distinct first-time "user" - a live property showed 156 "active users" in Realtime from what was actually a handful of real people browsing a few pages each (`page_view`/`first_visit`/`session_start` all landing within a few counts of each other is the signature of this). Global default-deny is the safest privacy posture but makes analytics close to useless for the ~all-US audience this site actually has.

Switched to region-scoped defaults instead: `analytics_storage` now defaults to **granted** globally, with a **denied** override (plus the opt-in banner) only for visitors GA4/the browser thinks are in the EEA/UK/Switzerland. Since this is a static site with no server-side geo lookup (the Worker only handles `/api/contact`, everything else is `env.ASSETS.fetch()` passthrough), the region check is a client-side heuristic - `Intl.DateTimeFormat().resolvedOptions().timeZone` starting with `Europe/` - not a real IP-based geo lookup. This is a best-effort approximation, not a legal guarantee: it over-includes a handful of non-EEA European countries (Russia, Turkey, etc. also use `Europe/*` zone names) into "ask first," which is a safe direction to be wrong in, but it can also be fooled by a changed OS clock/timezone or a VPN. If Doug ever needs precise, defensible geo-gating, that means real server-side detection (Cloudflare's Worker already sees `request.cf.country` for free - the site would need an `HTMLRewriter`-based edge injection instead of the current pure asset-passthrough to use it).

Both `BaseLayout.astro`'s head script and `consent.js` run the same timezone check independently (small, deliberate duplication of a one-line check rather than threading shared state between an inline head script and an external file). Verified manually the same way as before, across both branches: a US-timezone visit gets `analytics_storage: granted` with no banner ever shown; an EU-timezone visit gets `denied` by default and sees the banner, with Accept/Decline and the returning-visitor stored-choice path all behaving the same as the original implementation.

## SEO / GEO / traffic impact of this refactor (2026-09-08)

Net assessment: **structurally positive, if the eventual deploy is done carefully** - the port fixes exactly the crawlability gap the live site's own `blazor-wasm-geo-audit` blog post identified, while preserving everything that matters for ranking continuity.

**Why it should help:**
- The live site is a client-rendered Blazor WASM SPA - nothing real exists until ~3-4MB of WASM downloads and boots, which is why it needed a hand-maintained "static pre-paint" hack for the homepage plus a separate Playwright prerendering pipeline (`tools/prerender/`) just so crawlers see real content at all. This site needs none of that: every page is complete, real HTML at build time, for every crawler, on a plain GET - the exact thing that blog post audited as broken.
- Structured data (`Person`/`WebSite`/`SoftwareApplication` globally, `Services`/`FAQPage`/`BlogPosting` per-page) is baked directly into static HTML instead of depending on the prerender pass catching it correctly.
- Lighthouse's SEO category scores a clean 1.0 locally.

**Continuity preserved (the things that would otherwise reset rankings/history):**
- Same domain and identical URL structure for every route - Google recrawls URLs it already has indexed rather than needing to discover anything new.
- Same GA4 property ID (`G-3H1NB9ES0L`) carried over - no analytics history split.
- Canonical URLs, OG/Twitter meta, and `sitemap.xml` (now auto-generated by `@astrojs/sitemap` from actual routes instead of hand-maintained) all point at the same real domain throughout.

**One intentional content change worth remembering:** the homepage hero's visible subtitle changed from "software engineer building custom web apps..." to a sentence about the current ERP project - "software engineer" is now less prominent in the hero's actual on-page text (still present in the `Person` schema and `<title>`). Small, real keyword-emphasis shift, and it happens to point the same direction as the recruiter-visibility constraint above.

  **2026-09-20 investigation - conclusion: the "regression" was mostly measurement noise, not code.** Re-ran `npx lighthouse https://dougrosenbergdev.com` from this machine repeatedly post-deploy and got wildly inconsistent results across 8 runs in ~30 minutes on identical, unchanged deployed code: performance 0.67-0.84, LCP 4.3s-5.8s. Root cause of the noise found and partially fixed: an earlier local A/B test's `http-server` instances were accidentally left running in the background (a `kill` issued from a separate Bash shell doesn't affect a job started in another shell) for ~40 minutes, contending for this machine's CPU during every "live" Lighthouse run in between - killed, but 2 more clean runs still varied (0.76-0.77), so that wasn't the whole story either. **The real answer came from Google's own PageSpeed Insights infrastructure** (not this local machine): a fresh PSI run scored **84/100, LCP 4.4s** - matching the original 2026-09-10 baseline almost exactly, confirming there was never a real, stable regression to fix.
