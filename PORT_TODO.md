## SEO / GEO / traffic impact of this refactor (2026-09-08)

Net assessment: **structurally positive, if the eventual deploy is done carefully** - the port fixes exactly the crawlability gap the live site's own `blazor-wasm-geo-audit` blog post identified, while preserving everything that matters for ranking continuity.

**Why it should help:**
- The live site is a client-rendered Blazor WASM SPA - nothing real exists until ~3-4MB of WASM downloads and boots, which is why it needed a hand-maintained "static pre-paint" hack for the homepage plus a separate Playwright prerendering pipeline (`tools/prerender/`) just so crawlers see real content at all. This site needs none of that: every page is complete, real HTML at build time, for every crawler, on a plain GET - the exact thing that blog post audited as broken.
- Structured data (`Person`/`WebSite`/`SoftwareApplication` globally, `Services`/`FAQPage`/`BlogPosting` per-page) is baked directly into static HTML instead of depending on the prerender pass catching it correctly.
- Lighthouse's SEO category scores a clean 1.0 locally.

**Continuity preserved (the things that would otherwise reset rankings/history):**
- Same domain and identical URL structure for every route - Google recrawls URLs it already has indexed rather than needing to discover anything new.
- Same GA4 property ID (`G-3H1NB9ES0L`) carried over - no analytics history split.
- Canonical URLs, OG/Twitter meta, and `sitemap.xml` (now auto-generated by `@astrojs/sitemap` from actual routes instead of hand-maintained) all point at the same real domain throughout.

**One intentional content change worth remembering:** the homepage hero's visible subtitle changed from "software engineer building custom web apps..." to a sentence about the current ERP project - "software engineer" is now less prominent in the hero's actual on-page text (still present in the `Person` schema and `<title>`). Small, real keyword-emphasis shift, and it happens to point the same direction as the recruiter-visibility constraint above.

**Real gaps, not yet resolved:**
1. **IndexNow isn't carried over.** The live site's deploy step pings Bing/Yandex for instant indexing on every publish (key file + a step in `publish-gh-pages.yml`); this repo's `.github/workflows/` has no deploy step at all yet (matches the reference project's pattern of leaving deploy to Cloudflare's dashboard integration), so this mechanism needs re-adding somewhere before/at deploy.
2. ~~**Cloudflare's "Manage AI bot access" dashboard setting**~~ - resolved 2026-09-10. Set "Block AI training bots" → "Do not block (allow crawlers)" and "Manage your robots.txt" → "Disable robots.txt configuration" on the zone Overview page, same two settings as the music-site migration's `docs/todolist.md` playbook. Confirms this repo's actual `public/robots.txt` (`Allow: /`) now serves unmodified instead of Cloudflare injecting AI-crawler `Disallow` rules on top of it.
3. **The host migration itself is a real operational event** (GitHub Pages → Cloudflare Workers) even though the domain name doesn't change - different IPs/response headers. Now actually happened (2026-09-10: GitHub Pages unpublished on `PortfolioNov25`, Cloudflare confirmed serving the real domain) - noted here as a record that it went smoothly, not as a remaining risk.
4. ~~**`/previous` → `/archive` is a meta-refresh redirect, not a true HTTP 301**~~ - fixed 2026-09-10. Astro's static `redirects` config was a workaround for having no server at build time, but this site *does* have one - `src/worker.js` sits in front of every request already - so it now does `Response.redirect(new URL("/archive", url.origin), 301)` for `/previous`/`/previous/` before falling through to `env.ASSETS.fetch()`, and `astro.config.mjs`'s now-redundant `redirects` block was removed (confirmed `dist/previous/` no longer gets generated at all). Verified for real with `npx wrangler dev` (the only way to exercise `worker.js` locally - `astro dev`/`preview`/`http-server` all bypass it and serve static files directly) - real `HTTP/1.1 301` with the right `Location` header. Also noticed `/archive` and `/webdesign` both 307-redirect to their trailing-slash form on the *live* production site too (Cloudflare's static-assets directory normalization) - pre-existing platform behavior, not something this change touched or broke.

- Hero portrait now goes through `astro:assets` for a real responsive `srcset` (was serving one 840×1260 image at all viewport sizes; mobile now gets a ~7KB variant instead of 180KB).
- Fixed a genuine WCAG accessible-name mismatch on the header logo link (`aria-label` didn't include the visible "dr codeworks" text).
- `wrangler.jsonc` (assets-only, no worker script yet) and `public/_headers` (immutable caching for hashed `_astro/*` assets, weekly for hand-placed images/icons) written and ready.
- `.github/workflows/e2e.yml` + `lighthouse.yml` written, matching the reference project's pattern (no deploy step - Cloudflare's own dashboard git integration owns that). Won't execute until this becomes a real GitHub repo.
- `src/pages/404.astro` built (ported from the original `NotFound.razor`) - `wrangler.jsonc`'s `not_found_handling: "404-page"` now has something to serve.
